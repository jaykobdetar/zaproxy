# Build and launch Personal ZAP

From this fork's `feature/familiar-workspace` branch, on an Ubuntu desktop:

```bash
git clone --branch feature/familiar-workspace --single-branch https://github.com/jaykobdetar/zaproxy.git
cd zaproxy
./zap-personal
```

This builds the custom core and Private Evidence serially, then opens ZAP through
its unchanged upstream `zap.sh`. New profiles open the Traffic review layout.
Existing profile layout choices are retained. Literal Search and Private Evidence
are included; this is a development snapshot, not an official ZAP release.
New private profiles use ZAP's timestamped persisted-session option, so first
startup opens directly and session files remain under that profile's `zap/sessions/`.
Later launches retain the profile's session preferences. Open saved sessions
through ZAP's normal UI; the wrapper does not automatically reopen a previous session.

## Prerequisites

- Linux with Bash, Python 3.8+ and a full JDK 17+ (`java` and `javac`). Set
  `JAVA_HOME` if the JDK is not the default Java. Nothing installs system Java.
- An X11/XWayland desktop with `DISPLAY` set for launching Swing.
- At least 3 GiB available RAM and 2 GiB free disk for building, or 1 GiB
  available RAM for running. Larger fresh dependency caches can need more disk.
  Pause competing heavy jobs first. The builder checks host/container headroom.
- Network access for the first build: the pinned official Gradle wrapper,
  configured upstream Gradle/Maven registries, and official ZAP add-on releases.
  Downloaded add-ons are verified against upstream `main-add-ons.yml` SHA-256
  pins. No credentials, paid services or privileged installation are needed.

Java 17 and 21 were used for earlier core validation. Ubuntu/Linux is this
launcher's supported path; macOS, Windows and other Java versions remain unrun.
The wrapper can be invoked as `python3 zap-personal` if executable mode is lost.

## Commands

```bash
./zap-personal build             # Build only; a desktop is unnecessary
./zap-personal run               # Launch the latest successful build
./zap-personal run --fresh       # Create another separate profile
./zap-personal run --profile review  # Reuse a named private profile
./zap-personal start --offline   # Cached incremental build, then launch
./zap-personal build --offline   # Cached build only
./zap-personal --help
```

`start` is the default command and always performs an incremental build first.
`run` launches the existing runtime without dependency downloads; rebuild after
source changes. An offline build requires the wrapper, Maven/Gradle dependencies
and the three verified upstream add-ons to have been cached by an earlier online
build. A missing cache produces an error; it does not fetch an alternative.

Builds use one worker, no parallel execution and no persistent Gradle daemon.
Core Gradle heap is capped at 1 GiB, the add-on at 512 MiB, its tests at 192 MiB,
and the launched application at 640 MiB. The existing `GRADLE_USER_HOME` is honored
if supplied; otherwise the dependency cache is private to this checkout.

Only unchanged Network, Call Home and Common Library packages are bundled,
alongside locally built Private Evidence. The builder uses upstream `distFiles`
for the core, filtered startup script, exact runtime libraries and third-party
notices. Arbitrary developer plugins in `src/main/dist/plugin` are not bundled.
The core LICENSE and LEGALNOTICE are copied as well. Local runtime file hashes
are recorded and checked before launch.

## Profiles and recovery

Everything generated by the wrapper is under the ignored `.personal-zap/`:

- `builds/runtime-*`: immutable runtime copies; `current` identifies the latest
  successful build. A failed build leaves the previous pointer intact.
- `gradle/` and `downloads/`: dependency caches (unless Gradle's cache is overridden).
- `profiles/default/`: the separate persistent ZAP profile, Java home and Java
  preferences. `profiles/fresh-*` are additional profiles created with `--fresh`.
  `--profile NAME` uses another named profile within this same private directory;
  names allow 1–64 letters/digits/underscores/hyphens, starting with a letter/digit.

Normal `~/.ZAP` configuration, databases and Java preferences are not used by
the application. The upstream shell launcher may read its usual JVM properties
file, but the explicit heap override replaces those arguments. Existing JVM
option environment variables are cleared for this child process; application
home/preferences are explicitly isolated. The shell's `HOME` is unchanged.
No profile is automatically deleted. Save sessions through ZAP's usual UI and
keep backups before manually removing generated directories. These profiles can
contain private traffic and profile-local CA material; keep them out of Git.
The launcher does not install certificates into any system/browser trust store.

Concurrent builds are refused. A profile already in use is refused with guidance
to use `--fresh`; different fresh profiles can be opened independently. Close ZAP
normally before building again to conserve resources. Normal closing prompts
remain available to protect unsaved work.

## Safe startup and limits

Every launch uses ZAP's supported `-dir`, `-silent` and `-config` options. Safe
mode is forced, the API is disabled, and telemetry/update checks and automatic
add-on updates are suppressed. No URL, scan, automation
plan or browser launch is passed. No system/browser proxy or security setting
is changed. These are offline-review startup defaults, not an OS network sandbox:
upstream features and user-installed add-ons retain their own behavior.

Network 0.25 forcibly enables its main proxy, so the apparent
`network.localServers.mainProxy.enabled=false` setting does not prevent a
listener. This fork adds a small opt-in GUI startup guard controlled by the
process-only JVM property `org.zaproxy.zap.personal.offline=true`. The wrapper
sets it to skip all extension command-line startup, where Network starts its
listeners. Ordinary upstream launches without this property keep their behavior.
Extension command-line actions are unavailable through this wrapper. This does
not remove existing interactive tools or prevent a user/add-on from later
starting a network action. No listeners or traffic are started by the wrapper.

Common errors explain missing Java/full JDK, display, memory/disk, caches,
checksum mismatch, busy profiles/builds and incomplete or changed runtimes. For
integrity errors, preserve the affected data and rebuild. The wrapper never
cleans caches/profiles or installs prerequisites automatically.
